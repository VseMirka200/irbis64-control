# Участие в разработке

Спасибо за желание улучшить «ИРБИС64 Контроль». Проект принимает сообщения об ошибках, предложения, исправления кода, тесты и улучшения документации.

Перед работой ознакомьтесь с [архитектурой](ARCHITECTURE.md), [руководством пользователя](USER_GUIDE.md) и [кодексом поведения](../.github/CODE_OF_CONDUCT.md). Уязвимости передавайте по [политике безопасности](../.github/SECURITY.md), не раскрывая детали в публичном Issue.

## Подготовка окружения

Требуются Windows и Python 3.11 или новее. Основной и вспомогательный интерфейсы используют PyQt6; сборка выпуска выполняется через PyInstaller.

~~~powershell
git clone https://github.com/VseMirka200/irbis64-control.git
cd irbis64-control
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install "ruff>=0.6,<1"
~~~

Запуск основного окна:

~~~powershell
.\.venv\Scripts\python.exe -m irbis_control
~~~

Запуск отдельного инструмента подключения:

~~~powershell
.\.venv\Scripts\python.exe db_connector.py
~~~

## Сообщение об ошибке

Сначала проверьте открытые и закрытые Issues. В новом сообщении укажите:

- версию приложения и способ запуска: EXE или исходный код;
- версию Windows и, для исходников, Python;
- режим источника: сервер ИРБИС64 или TXT;
- выбранные типы реестров и режим результата;
- точную последовательность воспроизведения;
- ожидаемый и фактический результат;
- минимальный относящийся к проблеме фрагмент журнала;
- обезличенный пример данных, если он необходим.

Не публикуйте логины, пароли, адреса закрытых серверов, полные библиотечные базы, персональные данные и другие конфиденциальные сведения.

## Подготовка изменения

1. Создайте fork и отдельную ветку от актуальной `main`.
2. Ограничьте Pull Request одной логической задачей.
3. Сохраните существующие форматы, совместимые импорты и поведение, если задача явно не требует миграции.
4. Добавьте или обновите тесты.
5. Обновите README и документы в каталоге `docs` при изменении пользовательского поведения.
6. Опишите проблему, решение, риски и выполненные проверки.

Не включайте в коммит виртуальное окружение, кэши, сборки, журналы, пользовательские базы и созданные Excel-отчёты.

## Архитектурные требования

- бизнес-логику размещайте в `irbis_control/core`;
- файловые форматы, сеть и внешние сервисы изолируйте в `irbis_control/infrastructure`;
- не выполняйте сетевые и длительные файловые операции в главном потоке Qt;
- сохраняйте тонкими корневые точки входа `main.py` и `db_connector.py`;
- новые настройки должны иметь безопасное значение по умолчанию и читать предыдущую схему;
- комментарии и docstring пишите по-русски и объясняйте причину, а не очевидное действие;
- не оставляйте закомментированный, дублирующийся или временный код.

## Изменения данных

Код, который пишет в ИРБИС64 или TXT, должен сохранять применимые гарантии:

- явное подтверждение пользователя;
- предварительный просмотр либо понятное описание операции;
- повторную проверку серверной версии;
- rollback-копию или резервную копию;
- атомарную запись локальных файлов;
- идемпотентность добавления меток;
- сохранение посторонних значений при очистке.

Тестовые записи должны быть вымышленными или необратимо обезличенными.

## Проверки

Перед Pull Request выполните тот же основной набор, что и CI:

~~~powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m compileall -q irbis_control main.py db_connector.py
.\.venv\Scripts\python.exe scripts\run_tests.py
~~~

Для изменений интерфейса вручную проверьте запуск `main.py` и `db_connector.py` на Windows, масштабирование, светлую и тёмную темы, отмену фоновой операции и закрытие окон.

Для изменений ИРБИС используйте тестовый сервер или моки. Не проверяйте экспериментальный код массовой записью в рабочую базу.

## Версии и выпуски

Версия указывается в двух местах:

- `project.version` в `pyproject.toml`;
- `irbis_control.__version__` в `irbis_control/__init__.py`.

Значения должны совпадать. Выпуск запускается тегом вида `1.0.0` или `v1.0.0`; тег обязан соответствовать версии проекта. Workflow также можно запустить вручную для добавления артефактов в уже созданный релиз. Он собирает два EXE, установщик, ZIP-архив и `SHA256SUMS.txt`.

Для локальной сборки установщика нужен Inno Setup 6. Запустите `scripts\build_installer.bat`; готовый файл появится в `dist`.
